# V3 marketplace: reviewable PR plan

## Decision

Replace [PR #1299](https://github.com/alvinunreal/oh-my-opencode-slim/pull/1299)
with a stack of small, behavior-complete PRs. Do not split by its existing
commits or by file alone: subsequent commits repair invariants introduced by
the initial port, and several files contain more than one feature. Merge each
slice into `master` in dependency order; close #1299 in favor of the stack once
its work is represented there. This document is a plan, not a record of merged
work.

The assessment used PR head `e838a4ed` against base `e06fcfbb`: 101 files,
+22,359/−1,422 lines. About 12,607 added lines are tests/snapshots and 9,257
are production TypeScript. Sizes below estimate production changes only; keep
the corresponding tests in each PR.

These are dependency boundaries, not eleven independent branches. PRs 6 and 7
can be prepared independently after their prerequisites, but their shared
integration waits for PR 8. Release preparation, including any
`3.0.0-beta.14` bump and generated build metadata, is a separate decision
after the feature stack.

PR 8's first complete host snapshot freezes the managed agent policy and
projection for that plugin generation. Repeated config hooks and v2 agent
transform replays reapply that owned snapshot; later host-config changes do
not mutate it in place. A fresh host reload/generation captures the new
configuration. PR 10 is planned to expose desired-versus-live status and an
explicit reload path across that boundary, not to alter the registry's
per-generation immutability contract.

## Extraction rules

- **Keep fixes with their feature.** Inherited activation additions/removals
  belong in PR 4; interrupted package repair in PR 3; removal rollback in PR
  5; native permission corrections in PRs 7 and 9. Do not reproduce an
  intermediate known-broken commit just to preserve commit history.
- **Split mixed files by behavior.** The original `activation.test.ts` mixes
  persistence and runtime activation; `store.test.ts` mixes store and service;
  `registry.test.ts` mixes baseline registration and marketplace policy. Move
  the relevant cases with each slice rather than copying entire test files.
- **Treat startup as one boundary.** The registry changes when agents become
  available, who resolves final models, and which permission snapshot skill
  filtering consumes. Changes in `src/agents/index.ts`, `src/index.ts`,
  `src/v2/setup.ts` and the skill-filtering hook must land together in PR 8.
  Marketplace-specific branches then land in PR 9. Do not freeze an empty v2
  host snapshot or run context transforms before registry readiness.
- **Extract coherent modules while splitting.** Separate role construction,
  registry projection and marketplace capability policy instead of retaining
  the PR head's roughly 2,600-line `src/agents/index.ts`. Keep shared
  live-identity types below status reporting so the core registry does not
  depend on status/service. Add barrel exports only when their implementations
  land.
- **Serialize shared-file changes.** Assign one owner at a time to
  `src/index.ts`, `src/agents/index.ts`, config schema, package manifest and
  lockfile. Update prompt snapshots with the PR that changes prompts; preserve
  stable prompt/tool sets within a session.

## Review and validation gate for every PR

1. State the user-visible behavior and dependencies in the PR description;
   review against its immediate parent, not the entire original PR.
2. Include focused unit and integration tests for that slice. In particular,
   exercise store contention/rollback (3), inherited config and persistence
   (4–5), permission ceilings (7 and 9), v1/v2 startup parity and existing
   agent behavior (8–9), and disk-versus-live state (10).
3. Run `bun run check:ci`, `bun run typecheck`, `bun run build` and the relevant
   Bun tests. Run packed-artifact verification when exports or packaging
   change; run full `bun test` at integration milestones and before release.
4. Establish the test baseline on current `master` before extracting. PR #1299
   reported six full-suite failures; treat those as claims to verify, not a
   blanket allowance for failures in the new stack.
5. Rebase downstream PRs after each merge and rerun affected tests. Check that
   schema, docs, prompt snapshots and release artifacts reflect only the
   behavior actually introduced by that slice.
